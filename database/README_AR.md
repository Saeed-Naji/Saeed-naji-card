# قاعدة Supabase المقترحة — الموقع المؤسسي الجديد فقط

**الحالة: تصميم جاهز للمراجعة، لم يُنفّذ على أي قاعدة بيانات.**

## لماذا هذا الملف؟

يستضيف مستودع `Saeed-Naji/Saeed-naji-card` معاينة React للموقع المؤسسي الجديد. البيانات الحالية محلية وتجريبية. لن نستخدم مشروع Supabase القديم أو بياناته أو مفاتيحه.

الملف `SCHEMA_PROPOSAL_NOT_APPLIED.sql` هو **مقترح SQL** لتطبيقه مستقبلًا على مشروع Supabase **جديد مستقل** بعد اعتماد هويته. لا تنسخه إلى مشروع قديم.

## الجداول المقترحة

1. `corp_admin_members`: قائمة أعضاء إدارة المشروع الجديد؛ لا يستطيع الزائر تعديلها أو التسجيل كمدير.
2. `corp_products`: المنتجات، إظهارها للزائر أو إخفاؤها، المواصفات والحالة.
3. `corp_business_info`: بيانات المنشأة التي يجوز نشرها بعد اعتماد المدير؛ لا توضع فيها أي أسرار.
4. `corp_quote_requests`: طلبات عروض الأسعار الخاصة؛ لا يمكن للزائر قراءتها أو إرسالها مباشرةً إلى Data API.

جميع الجداول مفعّل عليها RLS، مع صلاحيات مُقيّدة. يظهر للزائر فقط المنتج الذي `visible=true` وبيانات الشركة المعتمدة `is_published=true`. التعديل على المنتجات والبيانات يتطلب عضوية الإدارة وتسجيل دخول Supabase Auth.

## الخطوات بالترتيب قبل ربط الموقع

1. أنشئ مشروع Supabase جديدًا خاصًا بموقع Saeed فقط، وحدد منطقة الاستضافة وأسلوب المصادقة. لا تلمس مشروع Flower Light القديم.
2. اختبر المشروع على بيئة staging أولًا. راجع ملف SQL مع المسؤول عن البيانات ثم استخدم Supabase CLI لإنشاء Migration رسمي داخل المشروع الجديد؛ لا تعتمد هذا الملف بصفته Migration منفذًا.
3. أنشئ حساب المدير عبر Supabase Auth بطريقة رسمية ثم، **في مشروع Saeed الجديد فقط**، اربط `auth.users.id` الخاص به بجدول `corp_admin_members` من SQL Editor الموثوق.
4. شغّل Supabase Security/Performance Advisors، واختبر سياسات RLS قبل توصيل لوحة React.
5. بعد نجاح الاختبارات، أدخل إعدادات الاتصال العامة `VITE_SUPABASE_URL` و`VITE_SUPABASE_PUBLISHABLE_KEY` في بيئة النشر الجديدة. لا تضع أبدًا `service_role` أو secret key في المتصفح أو GitHub.
6. ابنِ لوحة إدارة محمية بتسجيل الدخول، وطبّق صلاحيات RLS، واستبدل تخزين المنتجات المحلي بقاعدة البيانات. لا تكشف محرر `?admin=preview` الحالي للعامة.
7. قبل استقبال أي طلب فعلي، أنشئ Supabase Edge Function للتحقق من المدخلات وTurnstile وحدود الطلبات والتخزين، واحسم سياسة الخصوصية ومدة الاحتفاظ بالبيانات. لا تفتح `INSERT` مباشرًا للزوار على جدول الطلبات.
8. بعد ذلك فقط، أدخل بيانات المنشأة المعتمدة وصور ومواصفات المنتجات الحقيقية، واختبر على الهاتف والحاسوب ثم فعّل الإنتاج.

## اختبارات الصلاحيات المطلوبة

| الحالة | المتوقع |
|---|---|
| زائر مجهول يقرأ منتجًا مخفيًا | مرفوض / لا تعاد بياناته |
| زائر مجهول يقرأ منتجًا ظاهرًا | مسموح |
| زائر مجهول يحاول إضافة منتج أو طلب سعر مباشرة | مرفوض |
| مستخدم مسجّل ليس مديرًا يحاول تعديل منتج | مرفوض |
| مدير معتمد يسجل الدخول ويضيف منتجًا | مسموح |
| مدير يقرأ الطلبات | مسموح |
| زائر أو مستخدم عادي يقرأ الطلبات | مرفوض |
| مستخدم عادي يحاول إضافة نفسه لجدول الإدارة | مرفوض |

**تنبيه:** نجاح الفحص الثابت لملف SQL لا يثبت أمن قاعدة البيانات. يجب تنفيذ اختبارات RLS الحقيقية داخل مشروع تجريبي جديد قبل التشغيل الفعلي. لم يتم إنشاء أو تغيير أي مشروع Supabase عبر هذه الخطوة.

مصادر التحقق: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) و[تأمين البيانات](https://supabase.com/docs/guides/database/secure-data).
